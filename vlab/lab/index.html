Introduction

Services such as Chubby, etcd and ZooKeeper let many machines agree on who owns what: which worker is the leader, which job holds a lock. If the coordinator itself fails, everything built on it can corrupt data or stop.

This lab uses a lock service built from scratch: five replicas run the Raft consensus protocol, a lock state machine grants time-limited leases, and fencing tokens protect resources from stale clients. You crash nodes, cut the network and watch it recover.

Objective

You will learn to

  • Explain how a replicated lock service stays correct when machines fail.
  • Observe leader election, log replication and quorum commit in a live cluster.
  • Predict and verify the effect of crashes and network partitions.
  • Explain why fencing tokens are needed even when the lock service is correct.

How each experiment works

  1. Aim and Theory: read the idea (5-10 minutes).
  2. Pretest: check what you already know.
  3. Procedure and Simulation: follow guided steps; the lab checks each one for you.
  4. Posttest: see how much you improved.

Target audience

Undergraduate and postgraduate students of Distributed Systems, Cloud Computing and Advanced Cloud System Software Design. Basic networking and process concepts are assumed; no Raft background is needed.

Course alignment

Consensus and replication, leader election, leases and timeouts, quorum systems, the CAP trade-off, failure models (crash, partition), and safe use of locks with fencing tokens.
